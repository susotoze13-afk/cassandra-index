# Cassandra Index — Governance

**Версия документа:** 1.0
**Дата:** 2026-09-21
**Статус:** предпродакшен; документ обязателен к исполнению командами разработки,
data governance, юридической службы, UX/UI и редакции
(см. `docs/preproduction-decisions.md` — дословный текст брифа решений).

## 1. Роли и зоны ответственности

| Роль | Зона ответственности |
|---|---|
| **Editor-in-Chief** | Единственный Accountable за Flash Alert и тексты Critical Mode; SLA на проверку Flash Alert и текстов Critical Mode — не более 2 часов. Владеет текстами критического режима, порогами состояний, формулировками драйверов. Имеет право опубликовать Flash Alert в обход недельного цикла. |
| **Methodology Editor** | Методология (`METHODOLOGY.md`), численные пороги, журнал калибровки, список изменений, ломающих сопоставимость (§10). |
| **Data Governance Lead** | Региональная таксономия (ISO 3166-2), версионированный справочник регионов «город ↔ регион», логика город-представителя, политика спорных территорий. Не CTO и не фронтенд. |
| **Review Board (3–5 человек)** | Статистик, OSINT-специалист, региональный аналитик. Ревьюит изменения, ломающие сопоставимость (breaking changes) и открытые вопросы калибровки; не ревьюит оперативные тексты. |
| **Расчётная команда** | Код расчётного пайплайна (`calc/`) и сайта (`js/`); методологией не владеет — изменения формул инициирует через Methodology Editor. |
| **Внешний эксперт по коммуникациям** | Второй рецензент текстов Critical Mode (см. §2.3). |

### 1.1. Двойное ревью текстов Critical Mode

Каждый релиз текста Critical Mode проходит двойное ревью: Editor-in-Chief
(по существу состояния и порогов) + внешний эксперт по коммуникациям
(по формулировкам и лексике). Без двух подписей текст не публикуется.

### 1.2. Чек-лист проверки ссылок официальных источников

Перед публикацией каждая ссылка на официальный источник проверяется по трём
пунктам: **URL актуален** (не битая ссылка, не перенаправление на нерелевантную
страницу), **утверждение соответствует источнику** (числа и факты совпадают
с публикацией), **контекст не искажён** (цитата не противоречит общему смыслу
материала). Провал любого пункта — основание не публиковать наблюдение.

## 2. Flash Alert

Протокол внепланового алерта между недельными публикациями (METHODOLOGY.md §2.1).

### 2.1. Триггеры

- Событие с severity 2.0 по критериям Д1.4 или Д2.4;
- Д7.3 = 1 (вступление третьей стороны в конфликт).

Срабатывание триггера не меняет опубликованный снапшот: расчётная команда
получает сигнал из пайплайна, алерт публикуется отдельно.

### 2.2. RACI

| Действие | Responsible | Accountable | Consulted | Informed |
|---|---|---|---|---|
| Детектирование триггера в пайплайне | Расчётная команда | — | — | Editor-in-Chief |
| Решение о публикации алерта | — | **Editor-in-Chief** (один Accountable) | Methodology Editor | Вся команда |
| Текст и формулировки алерта | Editor-in-Chief | Editor-in-Chief | Внешний эксперт по коммуникациям | — |
| Запись в audit log (ID, источники, статус) | Расчётная команда | Editor-in-Chief | — | Аудитор по запросу |

**SLA:** не более 2 часов с момента подтверждения триггера.

### 2.3. Отзыв и статусы

- Если через **24 часа** событие не подтверждено вторым независимым кластером
  (§3), алерт переводится в статус «неподтверждённый» с явной пометкой.
- Каждый Flash Alert получает уникальный ID и запись в append-only журнале:
  кто инициировал, какие источники, когда подтверждён/опровергнут; в записи
  есть поля `status` и `revoked_at`.
- Событие-основание помечается флагом `flash_origin` в наблюдениях следующего
  расчётного окна.

### 2.4. Публикационный пайплайн

Детектор триггера и журнал готовят к запуску; автоматическая публикация алерта
на сайте — при появлении бэкенда/edge-слоя. До этого алерт публикует Editor-in-Chief
вручную по протоколу выше.

## 3. Независимость источников: whitelist кластеров A–F

Для MVP действует жёсткий whitelist кластеров происхождения; граф цитирований —
roadmap v1.x.

| Кластер | Состав |
|---|---|
| **A — mainstream** | Reuters, AP, Bloomberg и аналогичные независимые мировые агентства |
| **B — state-media** | Государственные СМИ (любых стран) |
| **C — registries** | Открытые реестры и госзакупки |
| **D — satellite-osint** | Спутниковый OSINT (Maxar, Planet) |
| **E — field-osint** | Полевой OSINT (подтверждаемые наземные наблюдения) |
| **F — financial** | Финансовые и рыночные данные |

Правила:

1. Два источника считаются **независимыми** только если они из разных кластеров
   whitelist. Кластер вне whitelist — ошибка валидации входа.
2. Источник с флагом `state_affiliated: true` (обязательное поле схемы) —
   государственные СМИ — **не считается независимым** от официальной позиции
   своего государства. Короборация двумя источниками одного кластера
   засчитывается как предупреждение, не как независимое подтверждение.
3. Матрица «источники × драйверы» — в `docs/provenance-matrix.md`.

### 3.1. Red team

Правило обновления (сам процесс — после запуска, см. §10): раз в квартал
предпринимается попытка «провести» один факт через два кластера как
независимый. **Успешный пронос обязателен к разбору:** обновляются правила
независимости §3 и Provenance Matrix. Молча переписывать матрицу нельзя —
изменение фиксируется в журнале калибровки версии.

## 4. Геолокация: провайдер, SLA, пороги уверенности

### 4.1. Провайдер

- Основной: **MaxMind GeoIP2 Enterprise**; fallback — **IP2Location**.
- SLA: доступность ≥ 99.9 %, latency < 50 мс, автоматический переход
  на fallback-провайдера.
- Заявленная провайдером точность (фиксируется вместе с выбором провайдера):
  ~99 % страна, ~80 % регион.

### 4.2. Пороги уверенности IP («никогда не гадать»)

Пороги — breaking-параметры: меняются только через версию методологии и ревью
(в справочнике регионов дублируются в параметрах справочника).

| Уверенность | Что показывать |
|---|---|
| City ≥ 80 % | Город |
| City 50–80 % | Административный центр региона (PPLC/PPLA по GeoNames) |
| City < 50 % | Только регион, без города |
| Region ≥ 90 % | Регион |
| Region < 90 % | Только страна или «Global» |
| Страна не определена или любая ось < 50 % | Глобальный индекс |

Логика детерминирована и зашита в справочник: никакой динамики или случайного
выбора города-представителя. Владелец логики — Data Governance Lead.

### 4.3. Валидация на GPS-выборке

Обязательная процедура (первый прогон — в первую неделю продакшена):
выборка **1000 запросов с известной геолокацией (GPS)**; правило поднятия
порога — если при confidence 80 % точность города < 80 %, порог cityConf
поднимается до достижения точности ≥ 80 %. Процедура обязательна уже сейчас;
сама выборка требует продакшен-трафика (отложено, §10).

### 4.4. Протокол логирования

- **Никогда не логировать сырой IP на бэкенде.** Логируются только хэш IP
  (с солью, необратимый) и полученный код региона.
- Если геолокация выполняется на бэкенде — IP удаляется или анонимизируется
  в течение 24 часов (основание: legitimate interest для функциональности).
- На бэкенд передаётся только анонимизированный код региона (`region=RU-MOW`).
- **Рекомендация:** не хранить IP вообще — обрабатывать в памяти, сохранять
  только производные (country, region, confidence) без привязки к
  идентификатору пользователя.
- Edge-геолокация (Cloudflare Workers) или браузерная геолокация — целевой
  паттерн: IP не попадает в инфраструктуру сервиса вообще.

## 5. Приватность: правовые основания

### 5.1. GDPR

IP-адрес — персональные данные (Recital 30). Правовое основание — законный
интерес (Art. 6(1)(f)) для базовой функциональности показа регионального
индекса; уведомление при первом визите.

### 5.2. 152-ФЗ — открытый блокер

С 2026 года IP, cookie и геолокация — персональные данные. Требуется
локализация хранения на территории РФ и согласие субъекта. **Edge-геолокация
вне РФ может быть нарушением — юридическая экспертиза обязательна.**
Статус: **открытый блокер, владелец — CTO + юрист**; запуск в РФ без заключения
экспертизы не производится (см. §10).

### 5.3. CCPA

IP — personal information. Требования: уведомление о сборе, право на отказ,
раскрытие при передаче третьим лицам. Сайт ничего не передаёт третьим лицам —
раскрытие пустое, это фиксируется явно в `privacy.html`.

### 5.4. Согласие на определение региона (opt-in / opt-out)

- **Сейчас (статический сайт, нет бэкенда):** opt-in для всех посетителей.
  Без бэкенда невозможно отличить юрисдикцию визита, поэтому единственное
  честное поведение — не определять регион до явного согласия. Согласие
  (`region_consent: granted/denied` + timestamp) хранится в localStorage,
  без привязки к IP. Отказ — регион не определяется, toast повторяется
  на следующем визите.
- **При появлении edge-слоя (обязательное поведение будущего):** opt-out для
  юрисдикций вне EU/UK/РФ — регион определяется автоматически с возможностью
  отключить; для EU/UK/РФ сохраняется opt-in. Ветка opt-out фиксируется здесь
  как обязательное требование к edge-слою, а не как опция.

## 6. Региональная таксономия и спорные территории

- Регионы — **ISO 3166-2**; города — GeoNames (координаты, население,
  иерархия); маппинг город → регион через `admin1_code`, приведённый к
  ISO 3166-2.
- Справочник версионированный, в репозитории, привязан к версии методологии;
  владелец — Data Governance Lead. Изменение таксономии — breaking change.
- **Политика спорных территорий (фиксируется заранее):** «город отображается
  в регионе, определённом ISO 3166-2, с нейтральной формулировкой без
  политических утверждений». В публичном UI нет contested-разметки.

## 7. Протокол изменений, ломающих сопоставимость (мостик)

При каждом изменении из списка METHODOLOGY.md §10:

1. Параллельный расчёт по старой и новой методологии в течение **4–8 недель**.
2. Публикация «мостика» между сериями: неделя-«мост» хранит baseline
   (значения по старой методологии) + delta разницы.
3. На графике тренда — явный разрыв серии между версиями методологии.
4. UI-баннер: «Методология обновлена до v.X, исторические данные могут быть
   несопоставимы» со ссылкой на changelog.

## 8. Терминология

Нормативное наименование продукта и метрики:
**«Cassandra Index: Global Conflict Anomaly Score»** — индекс аномальности,
не вероятность и не эмпирический перцентиль (METHODOLOGY.md §1.1: фактический
расчёт — взвешенная сумма + степенное сжатие + инерция — не даёт CDF).
Допустимо в UI: «Индекс 72 — Очень опасно», без числовых вероятностей;
запрещённая лексика — PRD §2.2, §11.5. Для EN-выката заголовка используется
transcreation на основе этого термина (сам transcreation — отложен, §10).

## 9. Дополнительные категории риска (отдельная модель)

Дополнительные измерения (PRD §4.5: «прямое военное столкновение»,
«риск применения ядерного оружия») — отдельная самостоятельная модель,
а не расширение основного индекса. Условия запуска:

1. Валидация на исторических эпизодах **до** любой публикации численных оценок;
2. Метрики валидации — **PR-AUC, log loss, reliability diagrams**;
   Brier score — вспомогательно, с оговоркой о редких событиях;
3. Walk-forward validation (rolling-origin), не подгонка под фиксированные якоря.

До выполнения условий публикуются только качественные категории
(Низкий / Средний / Высокий) с дисклеймером «Оценка состояния, а не прогноз даты».

## 10. Аудиторский след

- Изменения снапшотов фиксируются в append-only журнале с hash-цепочкой
  (9 обязательных полей записи — см. METHODOLOGY.md §10 и `calc/audit.js`).
- **Полный audit log выдаётся по запросу** файлом журнала из репозитория.
- Краткая форма (дата, причина, прежнее значение) публична: по клику на
  пометку «Historical snapshot» на сайте.

## 11. Критерий брака копирайта hero

Юзабилити-тест заголовка (5–10 респондентов; сам тест — после запуска, P2):
вопрос «Как вы понимаете эту фразу?». **Критерий брака:** если более 20 %
респондентов упоминают «время», «осталось» или «таймер» — копирайт бракуется
и переписывается. Рекомендуемая утвердительная форма: «Индекс 72 — Очень
опасно» / «Index 72 — Very dangerous».
