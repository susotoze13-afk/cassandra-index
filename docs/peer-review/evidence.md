# Протокол доказательства: что открывает клетку «Р»

Клетка «Р» в аудите означает: *«метод или результаты проходили независимую научную
либо редакционную проверку вне организации»*. Это описание факта, а не намерения.
Ниже — единственный разрешённый способ записать этот факт.

## 1. Что считается

| Форма | Считается | Условия |
|---|---|---|
| Рецензируемый журнал, решение «принято» (в том числе после доработки) | **Да**, полное основание | Внешние рецензенты, письменное решение, отчёты сохранены |
| Рецензируемый журнал, отказ с отчётами | **Нет** для клетки, **да** для архива | Факт проверки был, но метод не принят; клетка остаётся минусом |
| Редакционный обзор ПО (JOSS и аналоги), решение «принято» | **Да, с узким основанием** | Проверен код и воспроизводимость, не конструкт. В основании клетки это обязано быть написано словами «проверено ПО, не метод» |
| Независимый экспертный орган с публикуемым отчётом | **Да** | Рецензент вне проекта, отчёт доступен, решение письменное |
| Препринт, блог, соцсети, доклад | **Нет** | Видимость, не проверка |
| Заказная рецензия без публикуемого отчёта | **Нет** | Непроверяемое суждение |
| Самооценка, второй автор проекта, «коллега посмотрел» | **Нет** | Внутренняя проверка |

## 2. Что обязано лежать в репозитории

Файл `docs/peer-review/records/<YYYY-MM-DD>-<слаг-площадки>.json`:

```json
{
  "venue": "JOSS",
  "kind": "software-review",
  "scope": "software",
  "submitted": "2026-11-10",
  "decision": "accepted",
  "decided": "2026-12-08",
  "external": true,
  "url": "https://github.com/openjournals/joss-reviews/issues/NNNN",
  "summary": "Что именно проверялось и каким решением закончилось — одна-две фразы.",
  "reports": ["docs/peer-review/records/2026-12-08-joss-thread.md"]
}
```

Правила:

- `external` — только `true`. Ложное значение означает, что рецензирование не внешнее,
  и клетку не открывает.
- `decision` ∈ `accepted` | `accepted-with-revisions` | `rejected` | `in-review`.
  Клетку открывают первые два.
- `scope` ∈ `method` | `results` | `software`.
- `reports[]` — пути к сохранённым отчётам (markdown или pdf в том же каталоге).
  Решение без отчётов допускается, но тогда `summary` обязана назвать, что именно
  проверялось.
- Даты — ISO `YYYY-MM-DD`.

## 3. Как клетка открывается (порядок обязателен)

1. Положить запись и отчёты в `records/`.
2. В `docs/articles/indices-audit-app-source.md`:
   - в матрице у Cassandra Index столбец «Р» → `✔`;
   - в развёртке вместо строки «— внешнего рецензирования нет…» — формулировка из
     решения: площадка, дата, что проверялось. Для `kind: "software-review"` —
     обязательно словами «проверено ПО, не метод».
3. `node indices-audit-build.js --write` — балл, место и устойчивость считает
   генератор, а не рука. Ожидаемый результат: 85 баллов, 3-е место.
4. `node --test` — сторож `tests/peer-review.test.js` проверяет согласованность
   записи и матрицы в обе стороны.
5. `docs/articles/habr-indices-audit.md` — errata с датой и новыми числами.
6. Публичные формулировки («внешнего рецензирования нет») заменяются фактом. Если
   проверено только ПО — так и написано.

Обратное направление тоже обязательно: **нельзя** поставить `✔` в матрице, не
положив запись, — тест упадёт.

## 4. Чего этот протокол не делает

Не повышает «качество» проекта и не подтверждает, что индекс верен. Рецензирование
проверяет метод и его изложение; точность, предсказательная сила и конструктная
валидность остаются за границей шкалы аудита (раздел «Чего шкала не измеряет» в
статье). Открытая клетка «Р» означает «метод прошёл независимую проверку», а не
«числа правильные».

## 5. Текущее состояние

`records/` пуст. Клетка «Р» у Cassandra Index — минус. Матрица, страница аудита и
статья говорят «внешнего рецензирования нет». Это верно на 2026-10-25 и изменится
только появлением записи.
