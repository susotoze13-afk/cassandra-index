## Что остаётся вам (в этом порядке)

1. **Получить зелёный `node --test`.** Сейчас красен `tests/public-export.test.js`:
   вход недели 2026-10-25 правился параллельной сессией (+D9.1 и источники,
   `docs/backfill/2026-10-25-d9-sources.md`), а `data/public/*` ещё не пересобраны.
   Пересборка — задача той же сессии: она должна сначала пересчитать неделю
   (`node calc/calc.js --write 2026-10-25`), потом публичный слой
   (`node calc/public-export.js --write`). Если сессия остановлена — скажите, сделаю
   сам одним прогоном, но это перезапишет производные файлы чужой недели.
2. **Загрузить архив в Zenodo** (GitHub release → Zenodo, или вручную). Zenodo выдаст
   DOI версии 1.1.0.
3. **Заменить DOI** в `CITATION.cff`:
   `doi: "10.5281/zenodo.23458011"` → новый DOI версии 1.1.0.
   Концепт-DOI проекта (если он есть) — предпочтительнее: он не требует правки при
   каждом релизе. Проверить на странице записи Zenodo, какой из двух DOI какой.
4. **Прогнать `node --test`** ещё раз (паритет версии и цитирования).
5. **Поставить тег и GitHub release**: `git tag -a v1.1.0 -m "1.1.0"`, затем
   release из тега — это и есть версия, которую рецензирует JOSS.
6. **Подать в JOSS**, указав: репозиторий, версию `v1.1.0`, DOI архива.

## Почему нельзя было обойтись без поднятия версии

JOSS рецензирует не «текущий master», а заархивированную версию. При подаче с DOI
1.0.0 рецензент клонировал бы код без странового слоя, публичного контракта и 18
новых тестов — и первый же вопрос был бы о расхождении статьи и кода.
