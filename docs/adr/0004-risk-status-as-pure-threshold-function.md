# 0004. Статус риска — чистая функция порогов, а не поле данных

## Контекст

PRD §10 фиксирует шкалу состояний (0–20 Спокойно … 97–100 Экстремальная угроза) и §14.4 — маппинг состояний на палитру; R66 требует версионирования и документированного обоснования порогов; R09 запрещает «узкие диапазоны и необоснованную определённость». Вопрос: хранить ли статус текстом в данных снапшота или вычислять из индекса.

## Решение

Статус и тон — чистые функции модуля `risk`: `status(index)` применяет пороги §10 и возвращает ключ словаря, `tone(statusId)` и `deltaTone(change)` возвращают тона палитры. Пороги живут в одном месте (код модуля); версия методологии — поле в снапшоте, смена версии между неделями раскрывается UI (R61).

## Почему

Рассмотрен вариант «статус пишет модель в снапшот»: отвергнут — расходится шкала у разных недель (модель меняет пороги, старые снапшоты показывают статус по старым правилам или по новым, оба варианта непоследовательны), дублирует индекс и создаёт риск рассинхрона «индекс 75, а статус Критически опасно». Рассмотрен вариант «статусы в данных с валидацией»: отвергнут — усложняет схему без выигрыша, порогов всё равно одна нормативная таблица. Чистая функция даёт одно место для порогов (требование R66 «одно обоснование») и детерминированность: один индекс → один статус на всех неделях.

## Последствия

Смена порогов §10 требует правки кода и релиза сайта, а не только нового снапшота — исторические недели покажутся в свете новой шкалы, что надо осознавать при версионировании (R61 частично это прикрывает строкой раскрытия). Если снапшот придёт с индексом вне 0–100, поведение определяет код `risk` — краевые случаи надо держать в тестах. Тон палитры жёстко связан со статусом, поэтому правка §14.4 касается только `risk.tone`.
