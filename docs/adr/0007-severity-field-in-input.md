# 0007. Severity-поле во входной схеме счётных критериев

## Контекст

Методология v0.6–0.7 вводит severity-градацию счётных критериев
(`вклад = Σ sev_i / CAP`, sev ∈ {0.2, 0.5, 1.0, 2.0}, §4.1), но во входной схеме
(`calc/input/<week>.json`) отдельного поля нет: severity свёрнут в уже
нормированное `value`, и разложить вклад обратно на события невозможно. Без
поля нельзя ни применять градацию, ни детектировать Flash-триггер
(severity 2.0 по Д1.4/Д2.4 — METHODOLOGY.md §2.1).

## Решение

Счётные критерии входа могут нести `events: [0.2, 0.5, 1.0, 2.0]` вместо
готового `value`; движок нормирует `value = min(1, Σ sev / CAP)` (CAP = 5 из
`calc/params.js`, `severityValues` и `capCount`). Старые входы с готовым
`value` остаются валидны и считаются как раньше — обратная совместимость
трёх существующих демо-недель обязательна. Детектор Flash-триггера читает
severity напрямую из `events`.

## Почему

Отвергнуто оставить severity только в текстовом описании методологии — без
поля во входе градация не доезжает до расчёта, и один крупный эпизод
(вторжение) даёт тот же вклад, что одно локальное столкновение. Отвергнуто
обязательный переход всех входов на `events` — ломал бы непересчитываемую
демо-историю (AGENTS.md: недели 08-02…08-23 не пересчитываются). Отвергнуто
вычисление severity из величины `value` — нормировка необратима, события
теряются до записи.

## Последствия

Входная схема расширяется опциональным полем `events` на критерии; валидация
проверяет severity из фиксированного списка значений. Снапшот и сайт ничего
нового не требуют: публикуется уже нормированный вклад. Добавление `events` к
старой неделе — пересчёт чисел и запись в audit log по протоколу §10.
