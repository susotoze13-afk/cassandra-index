# 0009. ICU MessageFormat: собственное подмножество вместо react-i18next

## Контекст

Бриф (решение 5.9 плюрализации) требует ICU MessageFormat и называет
react-i18next с плагинами. Проект держит ноль зависимостей как жёсткое
архитектурное правило (AGENTS.md, PRD): сайт — чистый HTML/CSS/JS, любой
импорт npm/CDN — ошибка. Строки плюрализации сейчас склеены через `split(';')`
ручными правилами, что не масштабируется на RU-формы (one/few/many).

## Решение

В модуль `js/i18n.js` вносится собственное подмножество ICU MessageFormat:
интерполяция `{var}`, `{n, plural, one{…} few{…} many{…} other{…}}` и
`{x, select, …}`; CLDR-правила множественного числа RU (one/few/many, дробные
→ other) и EN (one/other). Все существующие `;`-строки мигрируют на ICU,
старый `split(';')` удаляется. Тесты покрывают формы 1, 2, 5, 21, 22, 25, 0
и дробные для RU и one/other для EN; неизвестная категория → other.
Fallback при невалидной строке — «N единиц» без склонения, как в брифе.

## Почему

react-i18next несовместим с нулевыми зависимостями: пакет, плагины и их
транзитивные зависимости ломают сборку (собственный мини-бандлер в `build.js`
не резолвит node_modules) и сценарий «открыть index.html двойным кликом».
Интент брифа — ICU-синтаксис, CLDR-правила и тесты на все формы, — а не
конкретный пакет; подмножество сохраняет интент целиком (зафиксировано
как допущение A3). Отвергнут ручной RU-алгоритм на if/else — дублирует CLDR,
не тестируемо на границах (дробные, 21/22/25) и расползается по новым языкам.

## Последствия

Парсер ICU — новый код в i18n, который нужно поддерживать вручную; полный ICU
(сложные селекторы, вложенные плюралы) не поддерживается — при потребности
расширяется подмножество, а не миграция на пакет. Словарь становится
единственным местом строк; конкатенация новых строк запрещена ревью.
Snapshot-строк ключевых экранов до/после миграции обязан совпасть (R62.2).
