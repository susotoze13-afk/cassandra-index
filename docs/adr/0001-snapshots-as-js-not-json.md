# 0001. Снапшоты недельных данных — JS-файлы, не JSON

## Контекст

PRD §9 и R63 дословно называют файлы снапшотов `global.json`, `regions.json`, `region-europe.json` и т.д. Сайт обязан работать по двойному клику (`file://`) и с любого статического хостинга без бэкенда и без сборки.

## Решение

Снапшоты хранятся как каталог `data/<YYYY-MM-DD>/{global,regions,region-<slug>,trend,drivers,sources}.js`; каждый файл подключается `<script src="...">` и кладёт данные в `window.CI_DATA`; загрузку всех недель делает `data/latest.js` через `document.write` (единственный синхронный способ без fetch на `file://`); модуль `data` нормализует и валидирует (`latest()`, `week(date?)`, `listWeeks()`, `validate(snapshot)`).

## Почему

Рассмотрены варианты: (1) `fetch('*.json')` — отвергнут: браузеры блокируют `fetch` по `file://` из-за CORS, ломается главный сценарий «открыть index.html двойным кликом»; (2) `*.json` через script-тег — технически невозможно, JSON не исполняется; (3) единый bundle данных — отвергнут: ломает требование «новая неделя подкладывается одной операцией без правки кода» (R63.1) и кэширование неизменяемых снапшотов (R72). Отступление от буквы R63 — осознанное: смысл требования (предвычисленные неизменяемые недельные снапшоты, потребляемые без бэкенда) сохранён, меняется только расширение и механизм подключения.

## Последствия

Имя `.js` вводит в заблуждение: файлы данных не исполняемы и не должны содержать логику. Валидация схемы обязана жить в `data.validate`, потому что битый JS-файл молча отдаст `undefined` вместо ошибки парсинга; сбой грузится как `{dataState:'unavailable', errors[]}`, а не как исключение. `document.write` выглядит как легаси-приём, но удалять его нельзя — без него на `file://` не загрузить список недель; смена версии `"version"` файла `latest.js` при пересохранении ломает тесты. Если появится HTTP-хостинг, переход на `fetch + .json` потребует правки модуля `data`, но не схемы данных.
