# 0002. Дефолтный регион — по часовому поясу браузера, не по IP

## Контекст

R46 требует дефолтное определение региона «приблизительно по IP», R83 фиксирует формулировку раскрытия про IP-обработку, R47 запрещает показывать пометку про IP и определять реальный город. Решение брифинга от 2026-09-20: «первый визит имитирует IP-детект по часовому поясу браузера (выбор не сохраняется)». Реальный IP-детект требует бэкенда и провайдера гео-данных — против нулевого бэкенда продукта.

## Решение

`Intl.DateTimeFormat().resolvedOptions().timeZone` маппится через таблицу IANA-префиксов в один из 6 регионов + город-представитель. Результат показывается сразу, в localStorage не пишется; нераспознанный пояс → нейтральный hero + CTA. Явный выбор пользователя хранится под `cassandra.region` только после его же действия. Правовые тексты (R83) формулируются дословно под будущий бэкенд, хотя в текущей сборке IP вообще не обрабатывается. HTML5 Geolocation — только по явному клику.

## Почему

Рассмотрены: (1) реальный IP-детект — отвергнут: нужен бэкенд, провайдер гео и GDPR/152-ФЗ проработка, всё это вынесено в «Вне рамок»; (2) геолокация по умолчанию — запрещена R47 (нельзя запрашивать GPS без явного действия); (3) нейтральный hero для всех первых визитов — отвергнут: ломает требование R04/R45 «свой регион виден без скролла с первого экрана» и пользовательскую историю «сразу вижу свой регион». Часовой пояс — единственный локально доступный, ничего не отправляющий сигнал, и его неточность безвредна: город — ярлык-представитель региона, а не геопозиция пользователя.

## Последствия

Точность ниже IP: VPN, корпоративные таймзоны и `Etc/UTC` дают «чужой» регион — приёмлемо, потому что выбор региона в один клик (R48). Текст раскрытия про IP в футере и privacy.html описывает обработку, которой в статической сборке нет, — это осознанная ложь на будущее, которую надо не забыть поправить при появлении бэкенда, иначе политика будет врать в обратную сторону. Метафора «IP-детект» сохраняется в текстах PRD, но в коде её нет.
