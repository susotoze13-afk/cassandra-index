# 0064. Публичный журнал прогнозов

**Дата:** 2026-10-18
**Статус:** реализовано (2026-10-18): `calc/ledger.js`,
`data/public/forecast-ledger.json`, раздел `#ledger` на `validation.html`; тест
`tests/ledger.test.js`

## Контекст

ADR 0049 дал схему форвардного якоря: файл `calc/input/anchors/forward-<неделя>.json`
с ожидаемым кластером, обоснованием и датой фиксации, плюс валидатор
`calc/forward-anchors.js`. Это решило вопрос пре-регистрации, но не вопрос
публикации: журнала «обещали — получилось» не было ни в репозитории, ни на сайте.
Факт (`observedCluster`) жил в редакционной таблице `docs/calibration-journal.md`,
то есть проверялся только тем, кто уже верит проекту.

Читателю нужен ответ на два разных вопроса, и их нельзя смешивать:

1. **Сбываются ли заявленные ожидания?** Это редакционные якоря.
2. **Умеет ли индекс предсказывать лучше наивного правила?** Это benchmark, а не
   прогноз проекта; он нужен как точка отсчёта, относительно которой вообще
   имеет смысл говорить о качестве.

## Решение

Публичный журнал — один файл `data/public/forecast-ledger.json`
(`schema: 'cassandra-index-forecast-ledger'`, `schema_version: 1`, конверт
лицензии CC BY 4.0) и раздел `#ledger` на `validation.html`. Собирается
`node calc/ledger.js --write` (в связке — `calc/backtest.js --write`).

### 1. Две породы записей, разные по смыслу

- **`editor`** — редакционный форвардный якорь из
  `calc/input/anchors/forward-<неделя>.json`, прошедший `validateForwardAnchor`.
  Это единственный вид записи, который является прогнозом проекта.
  Ожидание берётся из файла как есть и задним числом не пересчитывается.
- **`baseline`** — наивный benchmark, а не прогноз: ожидание = кластер прошлой
  опубликованной недели, направление — `flat` по построению. Он
  детерминированно восстанавливается из предыдущей недели цепочки
  `RECALC_WEEKS`, поэтому подкрутить его задним числом нельзя, но и записью в
  git до публикации он не является.

В JSON оба вида лежат в одном массиве `entries` (сортировка по `week`, затем
`kind`: `baseline` раньше `editor`), в `summary` — раздельные блоки, на странице
— разные подписи. Промахи baseline не подаются как промахи проекта.

### 2. Форма правила

- Кластер факта — `clusterOf(index)` по шкале `SCALE` из `js/risk.js` (ADR 0048).
- Направление — `directionOf(delta)` с мёртвой зоной `DIRECTION_DEADBAND = 2`
  пункта индекса: `|Δ| ≤ 2` — `flat`. Это правило прогноза, а не метрика
  сравнения рядов (там дедбенда нет).
- Исход по каждому полю отдельно: `outcome.cluster` и `outcome.direction` ∈
  `hit | miss | pending`. `pending` — факта нет (неделя не опубликована) или
  ожидание не задано; в `total` такие записи не входят и считаются отдельно в
  `pending`.
- Baseline строится только по неделям цепочки, начиная со второй: демо-недели
  1.0 (08-02…08-23) в журнал не входят, переход 08-23→08-30 — разрыв методик,
  а не промах.
- У `editor` направления в схеме якоря нет. Если редактор его не указал,
  `outcome.direction` остаётся `pending` — направление не выдумывается.

### 3. Иммутабельность: git-проверка порядка

Для редакционной записи требуется, чтобы **коммит добавления файла якоря был не
позже коммита добавления `data/<неделя>/week.js`**. Проверка идёт по локальной
истории git (`git log --diff-filter=A --format=%cI --reverse -- <path>`, шов
`gitProbe`):

- `verified: true` — порядок соблюдён;
- `verified: false` — файл якоря добавлен позже публикации, запись честно
  помечена;
- `verified: null` — история недоступна (мелкий клон, нет git, файл не в
  истории): это сказано на странице, а не выдаётся за «всё хорошо».

У `baseline` `verified: true` и `committedAt` = `published` предыдущей недели:
иммутабельность обеспечивается детерминизмом правила, а не git.

### 4. Промахи публикуются наравне с попаданиями

Отдельный блок `misses` — плоский список `{week, kind, field, expected, actual}`
по каждому несовпавшему полю; на странице это отдельный блок «Промахи» и
сводка `hits/total`. Промах не сворачивается в процент и не прячется в сноску.
Это осознанно: журнал без промахов бессмысленен, а baseline на текущих неделях
даёт реальные промахи по направлению.

### 5. Ретроспективные записи запрещены

Запись фиксируется до факта: файл якоря пишет редактор до `--write` недели.
Добавить якорь «после того, как стало известно» нельзя — это поймает
`verified: false`. `observedCluster` не выдумывается: без опубликованной недели
запись — `pending`, а не угаданный исход. Переписать ожидание в уже
закоммиченном файле тоже нельзя — это видно в истории git.

## Почему

- **Отвергнуто: один вид записи «прогноз проекта» на всё.** Baseline — правило,
  а не прогноз; смешивать его с якорями значило бы выдавать наивную инерцию за
  достижение проекта.
- **Отвергнуто: считать baseline только по неделям с якорем.** Тогда журнал
  стартовал бы пустым, а читатель не увидел бы даже точки отсчёта.
- **Отвергнуто: восстанавливать ожидание задним числом из факта.** Это
  превращает журнал в подгонку: любая запись всегда попадает.
- **Отвергнуто: прятать промахи в сводку.** Процент без списка скрывает, где
  именно правило ошиблось; публикация промахов — и есть accountability.
- **Отвергнуто: автоматически поднимать `verified` без git.** Ложное «всё
  хорошо» хуже явного `null`.

## Последствия

- Журнал не пуст на старте: baseline даёт записи сразу по всем пересчитанным
  неделям цепочки (кроме первой); редакционный блок пуст до первого
  `calc/input/anchors/forward-<неделя>.json`, и страница говорит это прямо.
- Зависимость от git: в окружении без истории проверка даёт `verified: null`.
  Это не ошибка сборки, а честный статус; в CI история есть (полный клон).
- Новый якорь = файл в `calc/input/anchors/` → `node calc/backtest.js --write`
  (или `node calc/ledger.js --write`) → тесты. Файл живёт до публикации недели,
  после — не редактируется.
- `data/public/forecast-ledger.json` — производный файл: руками не правится,
  паритет и детерминизм пинит `tests/ledger.test.js`.
- Параметры калибровки (`k`, веса, пороги §9) журналом не трогаются: ADR 0049
  замораживает их до 8 строк редакционной таблицы.
- Журнал — не замена `docs/calibration-journal.md`: там аудиторский след
  калибровки, здесь — публичная проверка ожиданий.
