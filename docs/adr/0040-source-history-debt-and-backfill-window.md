# 0040. История источников: причина слепоты, реестр отбраковки и окно дозабора

**Дата:** 2026-10-18
**Статус:** принято (реализовано в `calc/history-debt.js`, `calc/backfill-report.js`,
`calc/params.js`; схема входов расширена forward-only)

## Контекст

Вопрос прогона: «надо ли подключить базу данных?». Повод — при смене методологии
приходится заново собирать источники за прошлые недели: «отсутствует история
хранения всех источников за прошлые недели».

Проверка репозитория показала три вещи.

1. **Источники не теряются.** Каждый вход `calc/input/<week>.json` несёт top-level
   `sources` (R55, 20–82 записи), `data/<week>/sources.js` их публикует, git хранит
   все версии. По истории `calc/input/` (30 коммитов) счётчики только росли:
   08-30 → 29, 09-06 → 36, 09-13 → 34, 09-20 → 77, 10-04 → 54, 10-11 → 85,
   10-18 → 71. Удаления — точечные замены битых/выдуманных URL, все описаны
   в сообщениях коммитов. Хранилища достаточно; база данных ничего не добавляет.
2. **Не хватает не хранения, а покрытия.** Критерий, слепой в ту неделю, не имеет
   источников вообще: их не собирали. Из базы нельзя достать источник, который
   никогда не собирали. Поэтому пересчёт под новую методологию упирается не в
   доступ к данным, а в их отсутствие.
3. **Причина слепоты нигде не зафиксирована структурно.** Слепой критерий — это
   `criteria[id] = null`; `AGENTS.md` обещал «`covered:false` с аттестацией», но
   такой формы во входах нет, аттестация живёт прозой в `driverConfidence.reason`
   и местами неполна. Через год по входам нельзя отличить «критерия тогда не
   было» от «искали и не нашли».

Прецедент D4.6 (ADR 0021) показывает цену: при перевыпуске 3.0 критерий дособрали
редакционно за все 7 прошлых недель (12 новых fetch-verified записей, коммит
`2c795e8`). Издержки видны в том же следе: у 09-20 один из источников D4.6 —
Reuters с ответом `401` (значение опирается на недоступный текст), у 09-27
значение «частично не рыночное», в якорях источник D4.6 — формальное «зеркало
Д4.4» (`docs/calibration-journal.md:254`). Это реконструкция, а не данные тех
недель, и отличить её от собранного в неделю сейчас нечем.

## Решение

База данных не подключается. Вместо неё — три поля во входах и два чистых модуля.

### 1. Причина слепоты — отдельный enum

Вход недели может нести top-level `blindReasons: { "<criterionId>": reason }`:

| Значение | Смысл | Следствие |
|---|---|---|
| `not-collected` | критерия тогда не было / его не собирали | **долг истории**, закрывается дозабором |
| `searched-none` | искали и не нашли | честное отсутствие сигнала |
| `gate-failed` | нашли, но ворота независимости (§4.1.2) не пройдены | данные есть, ворот не прошли |

Отсутствие поля трактуется как `unknown` (старые входы не переписываются).
С `PARAMS.blindReasonFrom` (`2026-10-25`) причина обязательна для каждого слепого
критерия — проверка выдаёт **warning**, не ворота.

### 2. Происхождение записи

Источник (top-level R55-запись или ссылка критерия) может нести
`origin: 'collected-in-week' | 'editorial-backfill'`. Отсутствие поля = собрано
в неделю. У D4.6 прошлых недель проставлен `editorial-backfill`: серия не должна
выглядеть однородной, если часть её добавлена задним числом.

### 3. Реестр отбраковки

Вход недели может нести top-level `rejected[]`:

```json
{ "url": "https://…", "date": "2026-10-14", "reason": "out-of-window", "note": "…" }
```

`reason` — из фиксированного набора: `duplicate`, `out-of-window`,
`wrong-criterion`, `weak`, `unavailable`. Тексты статей не хранятся (вес,
копирайт, и 90 % из них — мусор). Реестр валидируется `validateRejected`
и даёт **warning**, не ворота: неделя с ценными данными не должна теряться
из-за кривой строки в отбраковке.

### 4. Окно дозабора

`PARAMS.backfillWindow = 4`, `PARAMS.backfillCriteria` — явный список id
(esc-критерии ∪ драйверы Д1/Д3/Д5/Д6/Д7, 39 из 46). Окно отсчитывается **от
недели, в которой критерий впервые покрыт**: дозабору подлежат до 4 непосредственно
предшествующих недель цепочки. Глубже — источник либо исчез, либо описывает уже
другую ситуацию; получилась бы «историческая реконструкция», а не данные.

Список правится осознанно в момент смены методологии — там же видна цена.

### 5. Учёт долга — чистый модуль, не снапшот

`calc/history-debt.js` (без сети, диска и DOM): `weekDebt`, `debtReport`,
`debtLine`, `backfillTasks`, `validateRejected`, `validateBlindReasons`.
`calc.js` печатает сводку строкой «долг истории: N критерий-недель по M неделям»
(плюс отдельно «причина неизвестна» и «ранние недели-скелеты»). В `data/`
долг не публикуется: на сайте это шум и вопрос «почему у вас дырки».

`calc/backfill-report.js [--window N] [--weeks a,b]` печатает чек-лист
«критерий × неделя × причина» и **ничего не собирает** — сеть и отбор остаются
за редактором (governance §10.1).

### 6. Ранний скелет — отдельная категория качества

Входы 08-30, 09-06, 09-13 до 2026-09-25 были скелетом с шаблонными/выдуманными
URL, позже заменёнными на реальные (`a28292c` → `5b0b56f`, `2709587`). Они несут
top-level `legacy_skeleton: true` и выводятся в отчёте отдельной строкой, чтобы
долг истории не смешивался с новым, а цифры не выглядели равноценными.
История не переписывается — только маркируется.

## Почему

- **Отвергнуто: подключить БД.** Хранение уже есть и полнее, чем нужно: входы,
  публикуемые `sources.js`, git-история. БД добавила бы сервер, бэкапы, миграции,
  секреты, PII (в форме есть почта) и точку отказа — при нулевом выигрыше
  в доступе. Дефицит покрытия ею не лечится в принципе.
- **Отвергнуто: полный backfill истории при каждой смене методологии.** Цена
  растёт линейно с длиной истории и никогда не заканчивается; именно эту работу
  прогон и хотел прекратить. При этом backfill задним числом заведомо опирается
  на источники, которых в ту неделю не было, — то есть на реконструкцию
  (см. издержки D4.6 выше).
- **Отвергнуто: молекулярная схема `covered:false` с обязательной аттестацией
  как воротами.** Переписывать 12 архивных входов ради формы — ретроспективная
  правка истории; ворота на аттестацию отклонили бы неделю с ценными данными
  из-за отсутствующей строки текста.
- **Отвергнуто: хранить полный корпус текстов на каждую неделю.** Вес, копирайт,
  и подавляющая часть прочитанного не относится к делу. Реестр `rejected[]`
  с URL + датой + причиной отвечает на вопрос «мы это видели?» за десятки строк.
- **Отвергнуто: считать долг в публикуемом снапшоте.** Читателю нужен индекс и
  честность данных недели, а не бухгалтерия пайплайна.

## Последствия

- Новые входы обязаны нести `blindReasons` для каждого слепого критерия
  (с 2026-10-25) и, по возможности, `rejected[]`; старые — как есть, `unknown`.
- `calc.js` печатает сводку долга в каждом прогоне; рост долга виден сразу.
- Смена методологии получает процедуру: новый критерий → строка в
  `PARAMS.backfillCriteria` → `node calc/backfill-report.js` → дозабор в окне 4
  недель → `editorial-backfill` на добавленных источниках.
- БД может понадобиться позже и по другой причине — например, при росте числа
  индексов и потребности в агрегациях/API. Тогда это будет отдельное решение
  под конкретную задачу, а не «потому что так правильно».
- Известное ограничение: `rejected[]` и `blindReasons` не попадают в
  публикуемые `data/<week>/sources.js` (они живут во входах); сайт о них
  не знает и знать не должен.
