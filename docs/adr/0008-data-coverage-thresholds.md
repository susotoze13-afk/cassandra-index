# 0008. Пороги покрытия данных 40 % / 20 % и условие Д1/Д2

## Контекст

Открытый вопрос PRD §19.4 (и методологии v0.7 §11): при какой доле драйверов
без данных снапшот не публикуется. Демо-недели покрывают 5 из 45 критериев —
без жёсткого порога сайт публиковал бы числа, за которыми стоит почти ничего,
а маскировка недостатка данных инерцией размывала бы ответственность.

## Решение

Трёхуровневая классификация по суммарному весу драйверов без данных
(`nullWeight = 1 − q`, §5.3):

| Условие | Публикация |
|---|---|
| `nullWeight > 0.4` **или** `null` по Д1 **или** `null` по Д2 | `insufficient` — основной индекс не публикуется (global = null) |
| `nullWeight` 0.2–0.4 | Публикация с пониженной уверенностью (`confidence='reduced'`, пометка «неполное покрытие») |
| `nullWeight < 0.2` | Полная публикация |

Числа живут в `calc/params.js` (`PARAMS.dataCoverage`: insufficient 0.4,
reduced 0.2, d1d2Required: true) и помечены breaking-параметрами.
Insufficient-неделя не рвёт цепочку инерции: следующая валидная неделя считает
от последнего валидного внутреннего значения; посетителю показывается
последний валидный снапшот с пометкой «Historical snapshot».

## Почему

Отвергнута публикация всегда с q-сжатием как единственным барьером — сжатие
занижает число, но не сигнализирует о причине, и при почти полном отсутствии
данных любое число ложно точно. Отвергнут порог по числу (а не весу) null
драйверов — драйверы несравнимы по весу, 1 из 9 без Д1/Д2 не то же, что 1 из 9
с ними. Отвергнут запрет публикации только при null Д1/Д2 — при 39 % молчащих
весов снапшот всё ещё опирается на меньшинство шкалы.

## Последствия

Три пересчитанные демо-недели (покрытие 5/45) станут `insufficient` — это
требуемое брифом поведение: hero покажет неделю 08-23 как Historical snapshot,
а не пересчитанные 60/58/57. Контракт снапшота допускает `global = null`
только при `dataState='insufficient'`. Изменение порогов — только ломающей
версией методологии (запись в списке §10 и в журнале калибровки).
