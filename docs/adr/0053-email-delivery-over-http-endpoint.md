# 0053: Email-доставка через HTTP-эндпоинт провайдера, а не SMTP-клиент

**Контекст**
Дайджест должен уходить на список адресов из автоматического прогона. У проекта ноль зависимостей и нет серверной части; SMTP-клиента в стандартной библиотеке нет.

**Решение**
Письмо отправляется обычным HTTPS-запросом на эндпоинт выбранного провайдера; адрес эндпоинта, токен, отправитель и получатели приходят из окружения. Конкретный провайдер в этой сборке не выбирается — отправка работает заглушкой, пока владелец не задаст значения.

**Почему**
HTTP-запрос есть в стандартной библиотеке, поэтому нулевая зависимость сохраняется, а доставка тестируется на поддельном ответе без сети. Отвергли SMTP-клиент: своего в библиотеке нет, а сторонний — прямое нарушение конвенции. Отвергли собственный релейный сервис: новая инфраструктура, свои секреты и дежурство ради одного письма в неделю. Отвергли SDK провайдера: та же зависимость, только завёрнутая.

**Последствия**
Форма запроса подчинена чужому API, и смена провайдера — правка кода, а не настройки. Провайдера выбирает владелец, и до этого email-канал мёртв. Ошибки приходят в чужой терминологии: нет общего понимания мягкого и жёсткого отказа, нет отчётов о доставке и отписках — всё это остаётся на стороне сервиса.
