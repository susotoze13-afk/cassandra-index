# Спецификация: Патчи информационной безопасности — проверка и push

## Задача

Владелец сайта получил от параллельного процесса аудит ИБ (`docs/security-review.md`,
находки F-01…F-08) с патчами, лежащими незакоммиченными в рабочем дереве. Он хочет,
чтобы перед выкатом кто-то независимо проверил, что патчи корректны и ничего не ломают,
а затем довёл их до продакшена — в этом репозитории push в master и есть выкат.

## Решение

Пять изменений рабочего дерева (deploy.yml, index.html, privacy.html, .gitignore,
.github/dependabot.yml) прошли независимую проверку по критериям ниже, закоммичены
раздельными логичными блоками и запушены в master; успех выката подтверждён прогоном
workflow и живым URL.

## Решения по реализации

- Проверка — только чтение и git: `node --test` (зелёный до пуша), сверка SHA через
  `gh api repos/actions/<name>/git/refs/tags/<tag>` и сравнение с аннотацией в yml,
  ручной разбор двух HTML на предмет inline-скриптов/стилей и внешних ресурсов.
  `node build.js` не требуется — `js/**` патчи не трогают.
- Коммит-гранулярность: раздельные коммиты по находкам (F-06 + dependabot; F-05;
  F-02; F-01) плюс отдельный коммит артефактов `.autopilot/` (дашборд, реестр, прогон) —
  чтобы история говорила, какой патч что закрыл, и чтобы служебное не смешивалось
  с безопасностью.
- Push в master — внешнее действие, санкционированное словами брифа («запуш их»);
  отдельного вопроса не требует. Выкат после push автоматический (deploy.yml).
- Остаточный риск F-01 (PII в истории git) по отчёту — решение за владельцем
  (перезапись истории); этот прогон историю не трогает.

## Границы и швы

Одна единица работы — «проверка + git», код не пишется, подразделений нет.
Единственный шов — внешние контракты, которые проверяются как данные: GitHub API
(теги → SHA), YAML deploy.yml, заголовки двух HTML-страниц. Публичных сигнатур
новых модулей не появляется; существующие швы тестов (`node --test`) — единственный
исполняемый контроль.
