# Спецификация: Ревью кода сборки 4.0, устранение недостатков, выкат в master

## Задача

Владелец хочет уверенности, что код последней большой сборки (методология 4.0,
ADR 0069) не содержит багов и недочётов, — и чтобы исправленное уехало
в опубликованный master одним выкатом.

## Решение

Независимое ревью кода диффа сборки 4.0 по стандартам репозитория, исправление
всех находок класса «исправить сейчас» (баги, ошибки, безопасность), зелёный
прогон всех тестов и пуш в master. Стилистические замечания и редакционные
пункты прошлой сборки — в отчёт, не в код.

## Решения по реализации

- Объём ревью — дифф сборки 4.0 (`b2bca23..b60089c` — ровно кодовые коммиты
  сборки; `b558ae9..HEAD` — то же множество, но фиксируем явные границы),
  кодовые пути: `calc/`, `js/`, сборщики, тесты. `data/**` и документация вне
  ревью кода — там свои ворота (пины тестов, linkcheck). Почему: «ревью кода»
  после сборки означает код этой сборки; полное ревью 89 тест-файлов и истории
  — отдельный заход.
- Ревью ведётся по трём осям: корректность (баги, граничные случаи),
  безопасность, соответствие конвенциям репозитория (чистые модули, ESM,
  i18n, округление на выходе). Почему: это стандарты, закреплённые в AGENTS.md.
- Находки классифицируются: «исправить сейчас» (дефект, деградация, риск
  данных/безопасности) → тикет-ремонт; «заметка» (стиль, предложение) →
  отчёт. Почему: правка всего подряд переписывает чужие зоны и раздувает дифф.
- Исправления выполняют исполнители-субагенты, один тикет — один коммит,
  правила коммитов репозитория сохраняются (подпись не требуется — ворота DCO
  для PR; оркестратор коммитит свои зоны).
- После каждой правки `js/**` — `node build.js` (бандлы коммитятся).
  Производные `data/public/*` пересобираются только CLI, руками не правятся.
- Пуш — последний шаг, после финального зелёного `node --test`. Пуш отдаёт
  всю сборку 4.0 (master сейчас ahead 9 относительно origin) — это
  намеренно: «запуш в мастер» без ограничений.
