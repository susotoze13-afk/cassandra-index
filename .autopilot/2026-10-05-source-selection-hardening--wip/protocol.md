# Протокол grilling: устранение слабых зон выбора источников

- **Дата:** 2026-10-05, сессия grilling (4 раунда, Q1–Q24)
- **Кто:** пользователь (решения) + агент (факты, опции, рекомендации)
- **Что:** дерево решений по трём слабым зонам комментария читателя (бриф в `brief.md`)
- **Почему:** комментарий бьёт в выбор источников, отсутствие репрезентативной выборки
  и путаницу «пропагандный фон ≠ события»
- **Воспроизведение:** решения реализуются тасками `tickets/NN-*.md`; ADR —
  `docs/adr/0019-*`, `docs/adr/0020-*`

## Раунд 1 — рамка (Q1–Q7)

| # | Вопрос | Решение |
|---|---|---|
| Q1 | Приоритет слабых зон | **(в)** зоны 1+3 — механизмами, зона 2 — честное раскрытие как limitation, без инженерии |
| Q2 | Фиксированная панель источников | **ядро + ротация**: обязательное ядро для сравнимости недель, тематическая ротация сверху; жёсткий whitelist доменов отвергнут |
| Q3 | Независимость как ворота | **Да**: ≥2 независимых кластера либо 1 primary/OSINT (Provisional Primary §4.1.2) |
| Q4 | Кто красной командой проверяет входы | **Дешёвый чек-лист 5–7 вопросов** перед `--write`, ответ — в audit-запись; не требует второго человека, не нарушает «отбор ручной» |
| Q5 | Замер устойчивости | **Да, ядро ответа**: leave-one-out пересчёт, численный разброс против тезиса «нарисовать что угодно» |
| Q6 | Публичность новой политики | **(в)** кратко на сайте (методология) + детально в governance |
| Q7 | Полуавтоматизация покрытия (RSS-кандидаты) | **Опциональный этап позже**, отдельное явное решение |

## Раунд 2 — структура (Q8–Q14)

| # | Вопрос | Решение |
|---|---|---|
| Q8 | Состав и хранение ядра | **Ядро на кластер (~10 доменов), двухслойно**: обоснование в `docs/governance.md`, машинный дубль `PARAMS.coreSources` → **warning, не ворота** (у ядра может не быть релевантных новостей в окне) |
| Q9 | Обратная совместимость ворот | **(в) forward-only**: опубликованное не пересчитывать; строка в governance «ворота действуют с недели 2026-10-11»; формулы не меняются → methodology остаётся «2.0» |
| Q10 | Ужесточение зона 3 (secondary vs primary) | **(в) + Q3**: основное ужесточение — ворота Q3; отдельное требование primary на события — эволюция позже, иначе спокойный месяц упрётся в «нет primary → нет публикации» |
| Q11 | Формат метрики устойчивости | **(б)** одно число max\|Δ\| на неделю, порог ~5 п.п., при превышении — пометка в quality-блоке; **только цепочка 2.0**; таблица по кластерам — в docs по желанию |
| Q12 | Место трёх bullet'ов на сайте | **(а)** секция «Методология», ключи `method.sources.*`, минимальная правка `js/i18n.js` + `js/sections/methodology.js`, без новых секций |
| Q13 | Статус red team чек-листа | **(а)** обязателен к заполнению, но **advisory**: блокируют только ворота Q3/линкчек; флаги видны в аудите |
| Q14 | Укладка и порядок | **(б)** сначала машинная часть (ворота, метрика, roster), потом документы и сайт; Q7 — отдельно позже |

## Раунд 3 — детали реализации (Q15–Q20)

| # | Вопрос | Решение |
|---|---|---|
| Q15 | Спецификация ворот | **(а)** ≥2 кластера ИЛИ ≥1 `primary\|OSINT`; `state_affiliated:true` primary **допустим с пометкой в чек-листе** (IAEA/ООН — первичка, резать = обнулить D2/D5); **(б)** проверка в `loadInput` рядом с `validateInputSources` — ошибка входа; **(в)** конкретная дата: **с недели 2026-10-11** |
| Q16 | Состав чек-листа | **Все 7 вопросов**; вопрос 2 (поиск опровержения) — самый сильный; 6 и 7 не объединять |
| Q17 | Алгоритм метрики | **Все домены + все кластеры**, одно число = max из двух тестов; поле `sensitivity` **опциональное** (старые недели валидны, фикстура `tests/data.test.js` не ломается); считает `calc.js` при `--write`, чистая функция в движке для тестов |
| Q18 | Список ядра | Таблица-черновик принята; принцип: **«каждый используемый кластер представлен ≥1 доменом»**, а не «лучшие СМИ» |
| Q19 | Черновик трёх bullet'ов | Принят как черновик на правку (см. Q21/Q22 по порогу и 4-му пункту) |
| Q20 | ADR и укладка | **(б) два ADR**: 0019 — машинные решения, 0020 — процедурные; план тасков — в `.autopilot` |

## Раунд 4 — замыкание (Q21–Q24)

| # | Вопрос | Решение |
|---|---|---|
| Q21 | Публиковать ли порог «5 пунктов» | **Публиковать как метод, не как обещание**: «чувствительность считается по каждому домену и кластеру недели; раскрываем результат, если он превышает 5 пунктов» — фиксирует метод и честность раскрытия, не обещает «≤5 = идеально» |
| Q22 | Четвёртый bullet «не пылесосим инфополе» | **(б)** → `method.gaps.5` (раздел ограничений); `method.sources.*` — только то, что делаем (выбор → проверка → устойчивость) |
| Q23 | Ядро при мёртвых кластерах D/E | **(б)** ядро = «по ≥1 домену из A, B, C, F» + честная строка «D/E не задействованы, кандидаты открыты»; попутно **исправить расхождение Bloomberg** (governance = A, данные 09-20 = F) — классификацию зафиксировать в `docs/provenance-matrix.md` |
| Q24 | Формат фиксации | **(в)** всё одним заходом: протокол (этот файл), два ADR, план тасков в `.autopilot` |

## Итог

Принято 14 решений (Q1–Q24), отвергнуто 6 альтернатив (жёсткий whitelist доменов,
retroactive пересчёт, отдельный stage ворот вместо `loadInput`, блокирующий чек-лист,
автоматический поиск источников, requirement primary на все события). Исполнение —
по `tickets/`, машинная часть первой волной, документы и сайт — второй.
