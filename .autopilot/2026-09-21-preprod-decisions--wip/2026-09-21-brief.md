## 2. Методология и статистика

### 2.1. Статистическая интерпретация индекса 0–100

**Решение:** Индекс — **Anomaly Score (индекс аномальности)**, не вероятность и не эмпирический перцентиль. Показывает нормированное отклонение от базовой линии мирного времени (2010–2019), откалиброванное по историческим якорям.

**Требования:**
- В публичном UI запрещены слова «вероятность», «шанс», «процент риска», «обратный отсчёт». Блокируется на контент-ревью (PRD §2.2).
- Внутренняя документация должна содержать явную сноску: фактический расчёт (взвешенная сумма + степенное сжатие + инерция) не даёт CDF; термин «перцентиль» не использовать в технических описаниях.
- Допустимо в UI: «Индекс 72 — Очень опасно» без числовых вероятностей.

**Владелец:** Methodology Editor.  
**Ссылка:** METHODOLOGY.md §1.1, PRD §2.2.

---

### 2.2. Калибровка 12-месячных вероятностей событий

**Решение:** До завершения rolling-origin бэктеста **запуск вероятностных оценок запрещён**. В продакшене — только качественные категории (Низкий / Средний / Высокий) с обязательным дисклеймером: «Оценка состояния, а не прогноз даты».

**Требования:**
- Для дополнительных категорий (ядерный риск, прямое столкновение) — отдельная модель, запускается только после валидации на исторических эпизодах.
- Метрики валидации: Precision-Recall AUC, log loss, reliability diagrams. Brier score — вспомогательно, с оговоркой о редких событиях.
- Walk-forward validation (rolling-origin), не подгонка под фиксированные якоря.

**Владелец:** Расчётная команда + статистик.  
**Ссылка:** METHODOLOGY.md §8, §13.

---

### 2.3. Обоснование порогов состояния (Журнал калибровки)

**Решение:** Продакшен невозможен без публикации **«Журнала калибровки»** — документа, где для каждого исторического якоря указано: при каких параметрах (k, веса, λ) якорь попадает в заявленный диапазон.

**Требования:**
- Таблица якорей расширяется: Карибский кризис 1962, Able Archer 1983, Kargil 1999, Грузия 2008, Крым 2014, Украина 2022, Йом-Кипур 1973, Ирак 2003.
- Для каждого якоря: тип кризиса (ядерный / конвенциональный / прокси), источник данных, целевой диапазон, обоснование.
- Журнал калибровки — публичный артефакт, привязанный к версии методологии.
- Итеративный подбор параметров до выполнения всех якорных попаданий; фиксация в журнале.

**Владелец:** Methodology Editor.  
**Ссылка:** METHODOLOGY.md §9, PRD §19.3.

---

### 2.4. Минимальное покрытие источников для публикации

**Решение:** Трёхуровневая система:

| Условие | Статус публикации |
|---|---|
| Суммарный вес `null` драйверов > 40% **или** `null` по Д1 **или** `null` по Д2 | `Insufficient data` — публикация основного индекса запрещена |
| Суммарный вес `null` драйверов 20–40% | Публикация с пониженной уверенностью, явная пометка «неполное покрытие» |
| Суммарный вес `null` драйверов < 20% | Полная публикация |

**Требования:**
- `Insufficient data` не маскируется инерцией: показывается последний валидный снапшот с пометкой «Historical snapshot».
- Порог 40% и условия по Д1/Д2 фиксируются в методологии как breaking-параметры.
- Глобальный коэффициент покрытия `q` отражается в бейдже уверенности (см. 5.8).

**Владелец:** Methodology Editor.  
**Ссылка:** METHODOLOGY.md §4.2, §11, PRD §19.4.

---

### 2.5. Событие между недельными публикациями (Flash Alert)

**Решение:** Механизм Flash Alert (§2.1). Триггеры: Д1.4, Д2.4 (severity 2.0), Д7.3. Публикуется внеплановый алерт, снапшот не изменяется.

**Требования:**
- **RACI-матрица:** один Accountable — Editor-in-Chief. Он имеет право нажать «Опубликовать Flash Alert» в обход недельного цикла. SLA — не более 2 часов с момента подтверждения триггера.
- **Отзыв:** если через 24 часа событие не подтверждено вторым независимым кластером, алерт переводится в статус «неподтверждённый» с явной пометкой.
- **Аудит:** каждый Flash Alert получает уникальный ID и запись в immutable log: кто инициировал, какие источники, когда подтверждён/опровергнут.
- **Интеграция:** событие помечается флагом `flash_origin` в наблюдениях следующего окна.

**Владелец:** Editor-in-Chief (Accountable), инженер (implement).  
**Ссылка:** METHODOLOGY.md §2.1, PRD §19.5.

---

### 2.6. Независимость источников

**Решение:** Для MVP — **жёсткий whitelist кластеров происхождения**. Граф цитирований — roadmap v1.x.

**Требования:**
- Фиксированные кластеры: Кластер A = Reuters/AP/Bloomberg; Кластер B = государственные СМИ страны X; Кластер C = открытые реестры и госзакупки; Кластер D = спутниковый OSINT (Maxar/Planet); Кластер E = полевой OSINT; Кластер F = финансовые и рыночные данные.
- Правило: 2 источника считаются независимыми, только если они из разных кластеров.
- Флаг `state_affiliated: true` для государственных СМИ; такие источники не считаются независимыми от официальной позиции своего государства.
- **Provenance Matrix** — таблица: строки — источники, столбцы — драйверы, ячейки — «главный / вторичный / не учитывается».
- **Red team** раз в квартал: попытка «провести» один факт через два кластера как независимый. При успехе — обновить правила.

**Владелец:** Инженер + Editor-in-Chief.  
**Ссылка:** METHODOLOGY.md §3.1, §4.1.3, PRD §19.8.

---

### 2.7. Изменения, нарушающие сопоставимость (Breaking changes)

**Решение:** Список breaking changes (§10) сохраняется. При любом таком изменении — обязательный UI-баннер.

**Требования:**
- Баннер: «Методология обновлена до v.X.X, исторические данные могут быть несопоставимы» со ссылкой на changelog.
- При breaking change: параллельный расчёт по старой и новой методологии в течение 4–8 недель, публикация «мостика» между сериями.
- На графике — явный разрыв серии между версиями.
- Публичный audit log изменений методологии: версия, причина, ссылка на анализ.

**Владелец:** Methodology Editor.  
**Ссылка:** METHODOLOGY.md §10.

## 3. Управление данными и аудит

### 3.1. Владелец редакторского ревью критического режима

**Решение:** Единственный Accountable — **Editor-in-Chief**. SLA на проверку Flash Alert и текстов Critical Mode — не более 2 часов.

**Требования:**
- Editor-in-Chief владеет текстами критического режима, порогами состояний, формулировками драйверов.
- Review Board (3–5 человек: статистик, OSINT-специалист, региональный аналитик) — для breaking changes, но не для оперативных текстов.
- Расчётная команда владеет кодом, но не методологией.
- Каждый релиз текста Critical Mode проходит двойное ревью: Editor-in-Chief + внешний эксперт по коммуникациям.
- Ссылки на официальные источники проверяются на актуальность URL, соответствие утверждению, отсутствие искажения контекста.

**Владелец:** Governance.  
**Ссылка:** METHODOLOGY.md §10, PRD §6.

---

### 3.2. Региональная таксономия и справочник «город ↔ регион»

**Решение:**
- **Регионы:** ISO 3166-2.
- **Города:** GADM (или GeoNames) — координаты, население, административная иерархия.
- **Маппинг:** через `admin1_code` GeoNames, приведённый к ISO 3166-2.
- **Владелец:** **Data Governance Lead** (не CTO, не фронтенд).
- **Хранение:** версионированный справочник в репозитории, привязанный к версии методологии.

**Требования:**
- Для спорных территорий политика фиксируется заранее: «город отображается в регионе, определённом ISO 3166-2, с нейтральной формулировкой без политических утверждений».
- Изменение таксономии — breaking change.

**Владелец:** Data Governance Lead.  
**Ссылка:** METHODOLOGY.md §4.1.8, §7, PRD §19.7.

---

### 3.3. Аудиторский след для изменённого снапшота

**Решение:** **Immutable log** (append-only) с криптографической верификацией (hash chain).

**Обязательные поля записи:**
- `snapshot_id` (оригинальный)
- `version_before`, `version_after`
- `changed_by` (ID сотрудника)
- `changed_at` (timestamp)
- `reason` (обязательное текстовое поле, например «Источник отозвал публикацию»)
- `parameters_changed`
- `recalculation_method`
- `diff` (что именно изменилось в значениях)
- `approved_by`

**Требования:**
- Данные хранятся как baseline + delta; после записи записи не удаляются и не изменяются.
- Публично: при клике на «Historical snapshot» — краткая справка: «Этот снапшот был пересчитан [дата]. Причина: [краткое описание]. Предыдущее значение: [N]. Изменение методологии: [ссылка]».
- Полный audit log — по запросу.

**Владелец:** Инженер.  
**Ссылка:** METHODOLOGY.md §10, PRD §19.9.

---

### 3.4. Город-представитель региона

**Решение:** Детерминированная логика, зашитая в справочник.

**Правила:**
- Если confidence города ≥ 80% — показывать этот город.
- Если confidence 50–80% — показывать **административный центр региона** (PPLC/PPLA по GeoNames).
- Если confidence < 50% — показывать только регион.
- Если регион не определён — глобальный индекс.

**Требования:**
- Никакой динамики или случайного выбора.
- Владелец логики — Data Governance Lead.
- Изменение порога confidence — breaking change.

**Владелец:** Data Governance Lead.  
**Ссылка:** METHODOLOGY.md §7, PRD §2.8, §5.7.

## 4. Техническая реализация и приватность

### 4.1. Геолокация по IP

**Решение:** **MaxMind GeoIP2** (Enterprise) или **IP2Location**.

**Требования:**
- Точность: ~99% страна, ~80% регион (заявляется провайдером).
- **Никогда не логировать сырой IP** на бэкенде.
- Логировать только хэш IP (с солью, необратимый) и полученный код региона.
- SLA: доступность ≥ 99.9%, latency < 50 мс, fallback на второго провайдера.
- Обязательная валидация: на выборке 1000 запросов с известной геолокацией (GPS) проверить точность; если при confidence 80% точность города < 80% — поднять порог.

**Владелец:** Инженер.  
**Ссылка:** METHODOLOGY.md §7.

---

### 4.2. Соответствие приватности: GDPR, 152-ФЗ, CCPA

**Решение:** **Edge-геолокация** — лучший паттерн. IP не попадает в вашу инфраструктуру.

**Требования:**
- Выполнять геолокацию на edge-уровне (Cloudflare Workers) или в браузере клиента.
- На бэкенд передавать только анонимизированный код региона (`region=RU-MOW`).
- Если геолокация на бэкенде — IP удаляется или анонимизируется в течение 24 часов (basis: legitimate interest для функциональности).
- **GDPR:** IP — персональные данные (Recital 30). Правовое основание — законный интерес (Art. 6(1)(f)) для базовой функциональности. Уведомление при первом визите.
- **152-ФЗ:** с 2026 IP, cookie, геолокация — персональные данные. Требуется локализация хранения на территории РФ и согласие субъекта. Edge-геолокация вне РФ может быть нарушением — юридическая экспертиза обязательна.
- **CCPA:** IP — personal information. Уведомление о сборе, право на отказ, раскрытие при передаче третьим лицам.
- **Рекомендация:** не хранить IP вообще. Обрабатывать in-memory, сохранять только производные (country, region, confidence) без привязки к идентификатору пользователя.

**Владелец:** CTO + Юрист.  
**Ссылка:** GDPR Recital 30, 152-ФЗ, CCPA.

---

### 4.3. Пороги уверенности IP

**Решение:** Строгие пороги, «никогда не гадать».

| Confidence | Что показывать |
|---|---|
| City ≥ 80% | Город |
| City 50–80% | Регион (административный центр) |
| Region < 90% | Только страна или «Global» |
| Любой < 50% | Глобальный индекс |

**Требования:**
- Лучше показать меньше, чем ввести в заблуждение (PRD §2.3).
- Пороги фиксируются в методологии как breaking-параметры.

**Владелец:** Инженер + Methodology Editor.  
**Ссылка:** PRD §2.3, §7.

## 5. UX/UI, локализация, доступность

### 5.1. Согласие на сохранение региона

**Решение:** Неблокирующий toast при первом визите: «Мы определили ваш регион для удобства. [Изменить]».

**Требования:**
- **EU/UK и Россия:** opt-in — по умолчанию регион не определяется, пока пользователь не согласится.
- **US/остальной мир:** opt-out — регион определяется, но есть возможность отключить.
- Хранение согласия: cookie или localStorage с флагом `region_consent: granted/denied` и timestamp. Не привязывать к IP.

**Владелец:** UX + Юрист.  
**Ссылка:** GDPR, 152-ФЗ.

---

### 5.2. Заголовок-вопрос и обратный отсчёт

**Решение:** Юзабилити-тест на 5–10 респондентах. Вопрос: «Как вы понимаете эту фразу?».

**Критерий:** если >20% упоминают «время», «осталось», «таймер» — копирайт бракуется и переписывается.

**Рекомендация:** для hero-блока использовать утвердительную формулировку: «Индекс 72 — Очень опасно» / «Index 72 — Very dangerous». Это универсально и не несёт риска обратного отсчёта.

**Владелец:** UX-исследователь.  
**Ссылка:** PRD §2.1, §15.

---

### 5.3. Мультиязычность заголовка

**Решение:** Избегать идиом. Использовать устоявшиеся термины: «Cassandra Index: Global Conflict Anomaly Score».

**Требования:**
- Не переводить дословно; использовать transcreation.
- Проверять обратный перевод.
- A/B-тест на каждом языке отдельно.
- Не использовать автоматический перевод для заголовков.

**Владелец:** UX + переводчик.  
**Ссылка:** PRD §5.

---

### 5.4. Поля источника

**Решение:** Минимальный набор + два дополнительных поля.

**Обязательные:**
- `id`, `title`, `domain`, `url`, `publication_date`, `accessed_date`, `source_type` (primary / secondary / OSINT), `cluster_id`, `state_affiliated` (boolean).

**Опциональные:**
- `author`, `archive_url`, `archive_date`, `confidence`, `notes`.

**Требование:** JSON Schema с валидацией при ingestion. Отсутствие обязательного поля — ошибка пайплайна.

**Владелец:** Инженер.  
**Ссылка:** METHODOLOGY.md §3.1, PRD §19.17.

---

### 5.5. Сортировка источников

**Решение:** Жёсткий алгоритм:
1. Тип (primary/OSINT выше secondary).
2. Дата (новые выше).
3. Домен (алфавитно).

**Требования:**
- Решение принимает Product Owner, алгоритм фиксируется в ТЗ.
- UI показывает порядок явно: иконка типа рядом с заголовком, tooltip: «Сортировка: primary → дата → алфавит».

**Владелец:** Product Owner.  
**Ссылка:** PRD §4.3.

---

### 5.6. Раскрытие списка источников

**Решение:** По умолчанию список свёрнут. Состояние разворота — только в **sessionStorage**.

**Требования:**
- При новом визите (через неделю) — дефолтное (свёрнутое) состояние.
- Если пользователь явно нажал «скрыть источники» — запомнить в sessionStorage с expiry 30 минут.

**Владелец:** UX + frontend.  
**Ссылка:** PRD §4.3.

---

### 5.7. Интерактивный тренд на сенсорных экранах

**Решение:** Тултипы с автозакрытием — **антипаттерн**. Тап открывает **bottom sheet** на мобильных.

**Требования:**
- Bottom sheet закрывается только по тапу вне области или по кнопке «X».
- Desktop: hover → tooltip; клавиатурный focus → тот же tooltip.
- Mobile: горизонтальный скролл по точкам с вибрацией при переходе к новой точке.
- Bottom sheet: `role="dialog"`, `aria-modal="true"`, фокус переходит на панель при открытии, возвращается при закрытии.

**Владелец:** UX + frontend.  
**Ссылка:** PRD §4.4.

---

### 5.8. Блок уверенности на первом экране

**Решение:** **Не удалять, а упрощать.**

**Требования:**
- На первом экране — компактный бейдж «Качество данных: Высокое / Среднее / Низкое» (на основе `q`).
- Детальная математика — в модальном окне.
- Если уверенность низкая — показывать индекс с явной пометкой «Предварительная оценка — неполное покрытие источников» и, возможно, не показывать в hero, а переносить в блок «Состояние данных».

**Обоснование:** сокрытие неопределённости снижает доверие в долгосрочной перспективе, когда модель ошибается. PRD §2.3 предостерегает от ложной точности.

**Владелец:** UX + Editor-in-Chief.  
**Ссылка:** PRD §2.3, §8.1.

---

### 5.9. Плюрализация и склонения

**Решение:** **Запретить конкатенацию строк** в коде. Использовать **ICU MessageFormat** (`react-i18next` с плагинами pluralization).

**Требования:**
- Не изобретать свои правила.
- Тестирование: для каждого языка — набор тестов на все формы (1, 2, 5, 21, 22, 25, 0, дробные).
- Если библиотека не проходит — fallback: «N единиц» вместо склонения.

**Владелец:** Frontend.  
**Ссылка:** ICU MessageFormat, CLDR plural rules.

### 5.10. Доступность подсказки на тренде

**Решение:** Трёхуровневая доступность.

**Требования:**
1. `aria-label` к каждой точке: «Дата: X, Индекс: Y, Состояние: Z». Для графика в целом — `aria-describedby` со сводкой.
2. **Скрытая HTML-таблица** под графиком, доступная скринридеру (класс `sr-only` или сворачиваемая таблица данных).
3. `aria-live="polite"` при навигации с клавиатуры: объявляет текущую точку.
4. Bottom sheet (см. 5.7) — `role="dialog"`, `aria-modal="true"`.

**Соответствие:** WCAG 2.1 SC 1.1.1 (Non-text Content).

**Владелец:** Frontend + a11y-специалист.  
**Ссылка:** WCAG 2.1 AA.

## 7. Дополнительные P0-исправления в методологии (патч)

Эти дефекты не входили в исходный список вопросов, но обязательны к устранению до продакшена.

### 7.1. Нормировка весов: исключить D8 из знаменателя эскалации

**Проблема:** в §5 шаг 3 `wᵢ' = (wᵢ · cᵢ) / Σⱼ (wⱼ · cⱼ)` — D8 входит в знаменатель, даже если `d₈ = 0`. Это занижает эскалационный скор.

**Патч:**
```
wᵢ' = (wᵢ · cᵢ) / Σ_{j ∈ E} (wⱼ · cⱼ),  E = {Д1…Д7, Д9}
I_agg = max(0, S + U − λ · w₈ · d₈)
```
где `w₈` — фиксированный или отдельно нормированный вес деэскалации.

**Владелец:** Methodology Editor + инженер.

---

### 7.2. Потолок Д9 при S=0

**Проблема:** в §4.3.5 `U := (ρ/(1−ρ))·S`. Если `S = 0`, то `U := 0` — Д9 полностью игнорируется, когда нет прямых сигналов. Это противоречит смыслу раннего предупреждения.

**Патч:**
```
U_max = min( ρ/(1−ρ) · S + U_abs,  U_abs )
```
где `U_abs` — абсолютный малый потолок (например, 5–10 пунктов шкалы). Или ввести отдельный «precursor band», показываемый рядом с основным индексом.

**Владелец:** Methodology Editor.

---

### 7.3. Severity-градация счётных критериев

**Проблема:** счётные критерии используют `n / CAP 5`. Одно крупное событие (вторжение) и одно локальное столкновение дают одинаковый вклад, если попали в Д1.4.

**Патч:** ввести severity-веса:
```
вклад = Σ sev_i / CAP,  sev_i ∈ {0.2, 0.5, 1.0, 2.0}
```
или отдельные критерии для «стратегического шока» (вторжение, первый ядерный сигнал, новый театр).

**Владелец:** Methodology Editor + инженер.

---

### 7.4. Региональная модель отклонения

**Проблема:** в §7 `I_region = I_global · (1 − e_r) + I_global^reg · e_r` даёт двойной счёт: региональные сигналы уже в `I_global`, и снова в `I_global^reg`.

**Патч:** перейти к модели отклонения:
```
I_region = I_global + e_r · Δ_region
Δ_region = f(региональные сигналы) − f(глобальные сигналы, кроме региональных)
```
Если региональных данных нет, `Δ_region = 0`, и `I_region = I_global`. Это устраняет двойной счёт и естественно реализует сжатие к глобальному.

**Владелец:** Methodology Editor + инженер.
