# Как внести вклад в Cassandra Index

Спасибо, что хотите помочь. Ниже — как предложить правку, что проверяется до
приёма и что вы подписываете.

## Как предложить правку

1. Сделайте форк репозитория и отдельную ветку под одну задачу.
2. Внесите изменение и прогоните проверки (см. ниже).
3. Откройте pull request: что меняется, зачем и как это проверено. Один PR —
   одна тема; правки, не связанные с задачей, лучше вынести отдельно.
4. Ответьте на замечания ревью. Если правка меняет поведение, добавьте или
   обновите тест в том же PR.

Прямой push в `master` — только у владельца и у автоматики еженедельного
пересчёта (`weekly-calc.yml`). Вклад идёт через pull request; коммит и push в
этом репозитории — по договорённости с владельцем. Если вы не владелец,
не пушьте в `master`.

## Требования к коду

- **Ноль зависимостей.** Только стандартная библиотека Node.js и браузера.
  Импорт npm-пакета или CDN — повод отклонить правку.
- **ESM.** Все модули — `import`/`export`; исключение — CommonJS-сборщик
  `build.js`, он уже такой.
- **Сайт без фреймворков.** DOM только через `document.createElement` и
  `textContent`, без `innerHTML` со строками. Пользовательские строки — через
  словарь `js/i18n.js`, а не литералами в разметке.
- **Цвета и состояния** — только токены из `css/styles.css`.
- **После правки `js/**`** обязательно `node build.js`: страницы грузят
  собранные `js/bundle*.js`, и без пересборки правка не попадёт на сайт.
- **Данные и производные файлы руками не правятся.** Снапшоты недель пишет
  `calc/calc.js --write`, публичный слой — `calc/public-export.js --write`,
  архив выпусков — `calc/digest-export.js --write`.
- **Лексика.** Индекс не называет дату войны и не является оценкой того,
  случится ли событие. В текстах не должно быть оборотов про порог или грань
  и метафоры часов.

## Проверки

Одна команда из корня, без аргументов:

```sh
node --test
```

Один файл: `node --test tests/<имя>.test.js`. Тесты не ходят в сеть и не требуют
установки пакетов; проверяются чистые функции и файлы на диске. Форма
`node --test tests/` на Windows падает — запускайте без аргументов.

Если правка касается расчёта недели, дополнительно нужен прогон
`node calc/calc.js <неделя>` (только печать): он показывает, как изменение
влияет на индекс, до записи файлов.

## Коммиты и DCO 1.1

Проект принимает вклад под **Developer Certificate of Origin 1.1**
(https://developercertificate.org/). Подписывая коммит, вы подтверждаете, что
имеете право передать этот вклад проекту под его лицензиями и что он не нарушает
чужих прав.

Подпись ставится trailer-строкой в сообщении коммита:

```sh
git commit -s -m "Правка: что и зачем"
```

`-s` добавляет в конец сообщения строку:

```
Signed-off-by: Ваше Имя <you@example.org>
```

Имя и адрес должны быть настоящими и совпадать с автором коммита. Если подпись
забыта, дописать её можно без переписывания истории:

```sh
git commit --amend -s --no-edit      # последний коммит
git rebase --signoff <base>          # несколько коммитов ветки
```

Каждый коммит в pull request должен быть подписан. Это проверяет CI
(`.github/workflows/dco.yml` → `tools/check-dco.js`); merge-коммиты нарушением
не считаются. **CLA не требуется**: отдельного соглашения о передаче прав
проект не просит, достаточно подписи DCO.

## Лицензия вклада

Принимая вклад, вы соглашаетесь, что он распространяется под лицензиями
проекта по типу материала: код — Apache License 2.0 (`LICENSE`), данные —
CC BY 4.0 (`LICENSE-DATA`), документы и тексты — CC BY 4.0 (`LICENSE-DOCS`).
Права на название, логотип и домен вкладом не передаются (`TRADEMARK.md`).

## Релизы и DOI

Релиз выпускает владелец. Порядок такой:

1. Поднять версию в `VERSION` (semver; это единственный источник версии) и
   синхронизировать `version:` в `CITATION.cff` — расхождение ловит тест.
2. Проверить `.zenodo.json` **до** релиза: `creators`, `title`, `license`,
   `keywords`, `upload_type: dataset`, `related_identifiers` на сайт. Файл
   читается при создании записи, после релиза его правка ничего не меняет.
3. Прогнать `node --test` и `node build.js`, закоммитить.
4. Поставить тег `v<VERSION>` (например, `v1.0.0`) и отправить его в репозиторий;
   из тега собрать GitHub Release.
5. Zenodo выдаёт DOI для выпуска. DOI вписывается в `CITATION.cff` (поле `doi`)
   и в раздел «Как цитировать» этого README; `date-released` в `CITATION.cff` —
   дата релиза, а не дата недели индекса.

Процедура включения репозитория в Zenodo — на стороне владельца: привязка
GitHub-аккаунта в Zenodo и включение репозитория делаются один раз, до первого
релиза.
